# 还没解决的问题

下面是从代码和现有测试确认的缺口。它不是扩展产品的计划；先把现有功能和维护边界整理稳。修改相关模块时同步更新这一页，不保留已经完成的待办。

## 1. 资源推荐与旧审核代码还没有收口

[ResourceCurate.jsx](../src/pages/ResourceCurate.jsx) 能提交推荐；`App.jsx` 没有审核页面，旧 `/manage` 和 `/atelier` 都回首页。`opsQueue.js` 仍带相册、审核和角色查询，`contentBackend.js` 保留对应写入。

应先把现用的资源提交与这些无人调用的审核函数分开，再决定停用推荐入口还是确定站外处理方式。不要为了让旧代码有用而重建管理后台。

## 2. 历史配置与服务隔离还没核验完

相册建表、存储桶和授权仍在多个 SQL 中；`App.css` 保留 Web3、黑客松等旧页面样式。Nginx 的 CSP 还允许 Solana devnet，却没有列出首页请求的 Open-Meteo 域名。配置是否已在生产生效未核验，不能直接推断线上故障或擅自执行 SQL。

部署脚本允许覆盖目标目录，未校验仓库和分支；Supabase 实例由环境变量指定。需要另行只读核对班级站和 Raccord 的实际服务、数据库与发布目标，才能判断生产是否真正隔离。

## 3. 自动检查还不能代替完整使用流程

导入边界已有 lint 约束，天气请求和动画生命周期也已有独立测试，但 hook 仍可持有传输层订阅。它不是完整的架构验证。

测试目前没有自动浏览器层；懒路由用空白作为加载状态，也没有捕获 chunk 加载失败的页面错误边界。Worker 只有聊天模块的单测；入口、CORS、限流和语音没有同等覆盖，Worker 本身还被 lint 忽略。

下一步应补少量最容易出错的流程验证，并补 Worker 检查范围。测试目标是发现真实顺序错误，不是单纯增加数量。

## 4. AI 服务的可用性与权限需要分开判断

页面要求登录，但 [Worker 入口](../worker/src/index.js) 没有验证 Supabase 会话。CORS 只限制浏览器跨域读取，不是接口身份认证；限流绑定失败时仍会继续处理请求。

语音默认走浏览器，Worker 语音接口仍保留且上游请求没有显式超时。聊天模型列表查询失败时会使用写死的候选名称，代码不能证明这些模型当前一定可用。不要在说明里承诺“免费”“始终可用”或“只有登录用户能调接口”。
